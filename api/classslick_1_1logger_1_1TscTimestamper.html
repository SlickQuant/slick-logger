Detailed Description

Nanosecond timestamps from the CPU's cycle counter.

system_clock::now() asks the OS for the time on every log call. This timestamper reads the CPU's time stamp counter instead and converts ticks to nanoseconds since the Unix epoch with one multiply, so entries keep full nanosecond resolution (the counter ticks faster than that on x86-64). On the Windows laptop it was measured on, now() took 25 ns against system_clock's 58 ns, which took 29 ns off a four-argument LOG_INFO.

It is anchored to system_clock: the constructor measures the counter's rate against steady_clock over calibration (a sleep, so construct it before the hot path starts), and every resync_interval the first caller past it re-anchors, refining the rate over everything measured since construction. Drift that has built up is slewed away over the next interval rather than stepped, so timestamps from one thread never go backwards; only a jump in the wall clock larger than a slew can absorb (more than 0.1% of the interval) is followed by a step, as system_clock itself would show it. Readers never wait on a re-anchor in progress.

Both calibration and resync_interval are at least 1 ms. A shorter one, 0 or negative included, is raised to 1 ms. Without that floor on resync_interval, every now() would pay for a re-anchor, which takes two clock reads.

Where the counter cannot stand in for a clock (x86 without an invariant TSC, as some virtual machines report, or an architecture with no counter), uses_cycle_counter() is false and now() is simply system_clock. The counter must also agree across cores, which it does on current x86 and ARM systems. On ARM64 its rate is fixed by the platform and can be much coarser: 24 MHz on Apple silicon, so ~42 ns steps there.
